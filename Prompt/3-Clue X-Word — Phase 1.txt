==================================================
1. PROJECT OVERVIEW
==================================================

PROJECT NAME:
3-Clue X-Word

PROJECT TYPE:
Crossword Puzzle Creation & Management Platform

INITIAL ADMINISTRATOR:
John Ward

PRIMARY PURPOSE:
Allow the administrator to manually create crossword puzzles, automatically extract and number the words, assign three clue levels to each word, save reusable words and clues in a dictionary, and publish puzzles for mobile users.

Every crossword puzzle uses a fixed 12×12 grid.

Every answer has three clues:
- Harder
- Medium
- Easier

The mobile application will eventually award different scores depending on which clue level the player uses.

The admin website must be designed with this future mobile functionality in mind.

GENERAL WORKFLOW:
1. Administrator logs into the website.
2. Administrator opens the dashboard.
3. Administrator creates a new crossword.
4. A blank 12×12 crossword grid appears.
5. Administrator manually enters letters to construct a crossword.
6. Administrator clicks DONE.
7. The system analyzes the grid.
8. The system identifies across and down words.
9. The system automatically assigns crossword clue numbers.
10. The system generates a word list.
11. The administrator enters three clues for every word.
12. Previously used words can retrieve existing clues from a dictionary.
13. The administrator reviews and validates the puzzle.
14. The puzzle is published and assigned a consecutive puzzle number.
15. The puzzle becomes available to the future mobile application through a secure, read-only API.

The administrator must also be able to save drafts, return later, and correct mistakes.

CRITICAL WORD DETECTION RULES:

A word may be horizontal (Across) or vertical (Down).

ACROSS START:
A cell starts an across word when:
1. It contains a letter.
2. The cell to the left is blocked, empty, or outside the board.
3. The cell to the right contains a letter.
4. The word continues through consecutive letters until reaching a blocked/empty cell or the board boundary.

DOWN START:
A cell starts a down word when:
1. It contains a letter.
2. The cell above is blocked, empty, or outside the board.
3. The cell below contains a letter.
4. The word continues through consecutive letters until reaching a blocked/empty cell or the board boundary.

Use words of at least two letters for extraction unless the final specification states otherwise.

NUMBERS:
Clue numbers must be automatically assigned in conventional crossword order:
- Scan top row to bottom row.
- Scan each row from left to right.
- Assign a number to every square beginning an Across or Down word.
- If both an Across and Down word begin at the same cell, they share the same number.

EXAMPLES:
1 Across: 1A
1 Down: 1D
5 Across: 5A
7 Down: 7D

WORD RECORD:
Each extracted word should include:
- Puzzle ID
- Word ID
- Clue number
- Direction (ACROSS or DOWN)
- Answer
- Length
- Start row
- Start column
- Ordered cell coordinates

Use zero-based indexes internally if convenient.
Display human-friendly row/column values when needed.

BLACK CELL GENERATION:
The original workflow allows the administrator to enter letters into a white matrix and click DONE.

The program should derive black cells from cells that contain no letters.

Also support explicit black-cell editing while composing.

Avoid treating an unfilled editor cell as a permanent blocker too early.

GRID VALIDATION:
- Exactly 144 cells
- Only valid A–Z letters or blocked/empty cells
- No characters outside A–Z
- No unintended one-letter entries
- No incomplete extracted words
- No inconsistent data
- Detect disconnected word groups if applicable
- Warn about orphaned letter cells
- Warn about conflicting edits

Do not silently modify administrator-entered letters.

On clicking DONE:
1. Normalize the grid.
2. Determine blocked squares.
3. Extract across words.
4. Extract down words.
5. Generate clue numbering.
6. Check for problems.
7. Present clear validation messages.
8. Generate the word list.
9. Navigate to the Clue Editor if the structure is acceptable.

IMPORTANT:
If the grid is edited after clues have been written:
- Preserve clues for unchanged words where possible.
- Identify newly created words.
- Identify removed words.
- Flag modified answers.
- Ask for confirmation before deleting associated puzzle-clue records.

7. GAME RULES TO PRESERVE FOR PHASE 2
==================================================

Do not build the Flutter gameplay interface yet.

However, the database and API must preserve everything needed for these rules.

The mobile app will use:

Harder Clue:
7 points per letter.
Background: Yellow / Orange.

Medium Clue:
5 points per letter.
Background: Pink.

Easier Clue:
3 points per letter.
Background: Blue.

Show Me:
0 points for revealed letters.
Background: White.

Note:
The earlier conversation and some illustrative designs disagree about the pink/blue mapping. For implementation, use the explicit mapping above from the detailed specification and keep it in a shared central configuration.

BACKGROUND COLOUR PRIORITY:
Yellow -> Pink -> Blue.
A less difficult clue can lower the points available for affected cells.

A crossing letter already assigned a lower-point clue colour should preserve that lower-point colour.

A letter that has been revealed using Show Me is zero-point and must preserve that status.

Solved letters become black text.

Unconfirmed letters appear as red text.

Gameplay must track:
- User-entered letters
- Confirmed letters
- Revealed letters
- Clue level viewed
- Square scoring state
- Solved words
- Crossword completion
- Per-letter score

The original specifications contain conflicting descriptions of whether Show Me reveals one letter or completes the remaining letters of a word.

Do not make an irreversible implementation decision on this without confirmation.

Design the data model so it can support either behaviour.

Each puzzle must have a maximum theoretical score determined by its actual non-blocked letter count multiplied by 7.

A letter must not be double-counted simply because it belongs to both an Across and Down word.

Keep the authoritative scoring rules separate from UI colours.

Do not implement player rankings using fabricated comparative statistics. The original specification proposes a transformed "players beaten" percentage; a real leaderboard must use genuine player results, or clearly label an alternative metric as an estimate rather than a real percentile.
